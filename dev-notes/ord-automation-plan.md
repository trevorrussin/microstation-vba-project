## Approach (staged; each stage ends with something verifiable)
0. **Learn the API offline.** Get a decompiler (ILSpy / `ilspycmd`, via `dotnet tool` if policy allows) or the Bentley "OpenRoads SDK" samples, and write down
   how to create: an Alignment (from PI/curve data), a Profile on it, a TerrainSurface (from points/breaklines/an existing DTM), a Corridor
   (template drop on an alignment+profile), cross-section drawing space, named boundaries/drawing models.
1. **A .NET add-in `WZTCCif.dll` loaded in ORD** exposing a small request/response protocol identical to the VBA bridge (request file in, response file out,
   triggered by a key-in the add-in registers). Python gets new bridge ops `CIF_*` through the same `Bridge` (so the QA guard, op recorder and
   fingerprint apply unchanged). First ops are READ-ONLY: `CIF_LIST_ALIGNMENTS`, `CIF_GET_ALIGNMENT` (PIs, stations), `CIF_LIST_PROFILES`,
   `CIF_LIST_CORRIDORS`, `CIF_LIST_TERRAINS`, `CIF_GET_PROFILE_ELEVATIONS`.
2. **Creation ops, tested only in a scratch DGN** (seeded from the ORD seed; the engineer opens it - the rule is never switch files): create alignment,
   profile, terrain, corridor, cross-section/drawing models; each op read-back verified against the input data.
3. **Build runner** (`scripts/build_runner.py`): executes a playbook as a real build for a project spec, doing every agent step, using the `CIF_*` ops for
   creation steps, handing off only what the SDK cannot do, verifying after each step, and running the QA gate (with `--rel` checks) at the end.
4. **Drawing production**: plan sheets / profile sheets / cross-section sheets from named boundaries (MicroStation drawing-model + sheet-model APIs), annotation
   with style-matched text (PLACE_TEXT_LABEL now accepts `match_text_id` / `height` / `width`: uncommitted, hot-reloaded, NOT yet live-tested).

## Decisions needed from the engineer before stage 1 touches ORD
1. OK to load our own (unsigned, locally compiled) managed add-in into the live OpenRoads session? Corporate policy / IT approval may apply.
2. A scratch DGN (ORD seed, correct coordinate system) open for creation tests - never create civil objects in the 727 production file to "see what happens".
3. Inputs for the first 727 build: where the terrain data, alignment definitions (PI table / as-built geometry) and the corridor template live.

## Risks
- Loading managed code into a live ORD session can destabilise it; crashes lose unsaved work. Mitigation: read-only first, save before each load, scratch file for creation.
- Civil elements are intelligent objects with graph dependencies; deleting test objects is not always clean. Hence scratch file only.
- The SDK may not expose every tutorial step (e.g. some Create Drawing / annotation-group tools); those stay `who: engineer` with a verified handoff.
